# v0.7.0 Smoke Checklist — Two Roads Brewing Pilot

> Date: 2026-06-01
> Plugin version: 0.7.0
> Pilot site: `two-roads-brewing.local` (Local by Flywheel)
> Prerequisite: Two Roads' Local app is **running** (its PHP-FPM service must be reachable — without that, every probe below returns 502)

## Why this exists

v0.7.0 ships a substantial production-sync surface (new pagination / ordering / incremental-sync / ID-slug-taxonomy filters, plus new REQUIRED `modified` / `modified_gmt` row fields, plus a new `/jab/v1/site` endpoint). Unit tests cover the input → WP_Query mapping by reflection, but they do NOT exercise:

- `WP_Query` actually honoring the new `orderby` / `date_query` / `post__in` / `tax_query` clauses against real database state
- REST output validation of the new REQUIRED `modified` / `modified_gmt` against real post rows (including zero-date drafts that hit the fallback chain)
- The new `/jab/v1/site` endpoint returning the right values against a live theme + ACF + custom logo
- Application Password authentication working through the new `jab/headless_kit/manifest_capability` and `jab/headless_kit/site_manifest_capability` filters

This checklist walks an operator through proving each of those against the Two Roads install before tagging `plugin-v0.7.0`.

## Setup (one time)

1. Open Local by Flywheel.
2. Start the `two-roads-brewing` site. Wait for the green dot.
3. The plugin is already live via a symlink — `wp-content/plugins/wp-headless` → `C:\Projects\wp-headless\packages\wp-plugin`. **No upload needed.** Confirm the active version in WP Admin → Plugins reads `0.7.0`.
4. WP Admin → Users → your service-user account → scroll to **Application Passwords** → generate a new password labeled `jab-v0.7.0-smoke`. Save the credentials:

   ```bash
   export TR_BASE="https://two-roads-brewing.local"
   export TR_AUTH="-u <username>:<the-application-password-with-spaces>"
   ```

   (Application Passwords arrive space-separated like `xxxx yyyy zzzz`. Pass them through to `-u` verbatim — `curl` handles the quoting via shell.)

5. Two Roads' `beer` CPT is the right smoke target — it has real ACF fields, real Gutenberg blocks, real taxonomies (`beer-type`, `beer-status`). Everything that follows uses `jab/get-beers` and `jab/get-beer-by-slug`.

## Smoke 1 — plugin loads cleanly

```bash
curl -ks "$TR_BASE/wp-json/jab/v1/" | jq
```

**Expect:**
```json
{
  "ok": true,
  "name": "wp-headless-kit",
  "version": "0.7.0"
}
```

**Fail modes:**
- `502` → Local's PHP-FPM not running. Start Local.
- `500` → fatal in plugin load path. Check `wp-content/debug.log` for the stack trace; the `tests/bootstrap.php` stubs guard against the most common cases but a real WP runtime can surface integration issues.
- `404` → plugin not activated. Check WP Admin → Plugins.
- Version field anything other than `"0.7.0"` → the symlink isn't pointing where you think it is, OR you have a stale composer autoload cache. Run `composer dump-autoload -o` in `packages/wp-plugin/`.

## Smoke 2 — abilities register without `WP_DEBUG` noise

WP Admin → Tools → Site Health → **Info** tab (or `wp-admin/site-health.php?tab=debug`). Verify:

- No new `_doing_it_wrong` notices about JAB.
- `debug.log` (in `wp-content/`) has no warnings or notices since the last plugin restart.

If you see anything mentioning `Schema::diagnostics`, that's the ACF Options skip ledger — informational, not a fail.

## Smoke 3 — manifest endpoint still works with the new filter

```bash
# Default capability ("read") — every Application Password user can fetch.
curl -ks $TR_AUTH "$TR_BASE/wp-json/jab/v1/manifest" | jq '.plugin_version, (.abilities | length)'
```

**Expect:** `"0.7.0"` and a positive integer (one per registered `jab/*` ability).

```bash
# Run a focused regression on a single ability to confirm the new input schema landed.
curl -ks $TR_AUTH "$TR_BASE/wp-json/jab/v1/manifest" | \
  jq '.abilities[] | select(.name == "jab/get-beers") | .input_schema.properties | keys'
```

**Expect:** an array containing all of `["date_after","date_before","exclude_ids","include","include_ids","modified_after","modified_before","numberposts","offset","order","orderby","page","post_status","slug_in","taxonomy"]`.

## Smoke 4 — new `/site` endpoint (the v0.7.0 marquee feature)

```bash
curl -ks $TR_AUTH "$TR_BASE/wp-json/jab/v1/site" | jq
```

**Expect** every top-level key present: `plugin_version`, `generated_at`, `site`, `front_page`, `branding`, `menus`, `image_sizes`, `theme`.

Sanity checks against the live install:

- `site.title` matches WP Admin → Settings → General → Site Title.
- `site.home_url` is `https://two-roads-brewing.local`.
- `site.timezone` is whatever's in Settings → General.
- `front_page.show_on_front` is `"page"` (Two Roads uses a static homepage) and `front_page.static_front.slug` is the homepage's slug.
- `branding.custom_logo_url` is a real URL pointing into `wp-content/uploads/` — not `null`.
- `menus` includes the primary header location (and any others the theme declares).
- `theme.slug` is the active theme's stylesheet directory name.

If `branding.custom_logo_url` is `null` but you've set a custom logo, the most likely cause is the active theme not registering `custom-logo` support — that's a theme issue, not a plugin bug, but worth noting.

## Smoke 5 — pagination + ordering determinism (SYNC-1)

```bash
# Page 1 of beers, default order (modified-tiebroken DESC).
curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"numberposts":5,"page":1,"orderby":"date","order":"desc"}}}}' \
  | jq '.result.beers | map(.id)'

# Page 2 — must NOT overlap with page 1's IDs.
curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"numberposts":5,"page":2,"orderby":"date","order":"desc"}}}}' \
  | jq '.result.beers | map(.id)'
```

**Expect:** two non-overlapping arrays of 5 integer IDs each. (If `set(page_1) ∩ set(page_2) != ∅`, the ID tiebreaker isn't doing its job — file a regression.)

## Smoke 6 — incremental sync window (SYNC-2)

```bash
# Find a beer's modified timestamp, then ask for everything modified at or after it.
LAST_MODIFIED=$(curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"numberposts":1,"orderby":"modified","order":"desc"}}}}' \
  | jq -r '.result.beers[0].modified_gmt')

echo "Most-recently modified beer at: $LAST_MODIFIED"

curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":2,\"method\":\"tools/call\",\"params\":{\"name\":\"mcp-adapter/execute-ability\",\"arguments\":{\"name\":\"jab/get-beers\",\"arguments\":{\"modified_after\":\"$LAST_MODIFIED\",\"orderby\":\"modified\"}}}}" \
  | jq '.result.beers | length, map(.modified_gmt)'
```

**Expect:** the second call returns at least 1 beer (the same beer whose `modified_gmt` is exactly `$LAST_MODIFIED`, since the window is inclusive). Every returned `modified_gmt` is `≥ $LAST_MODIFIED`.

## Smoke 7 — `include_ids` auto-raise (SYNC-3, the silent-truncation guard)

```bash
# Get 30 known beer IDs.
KNOWN_IDS=$(curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"numberposts":30}}}}' \
  | jq -c '.result.beers | map(.id)')

echo "Asking for $KNOWN_IDS without setting numberposts (default would be ~25)"

# Refetch all 30 by ID — without setting numberposts. Auto-raise must give us all 30.
curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":2,\"method\":\"tools/call\",\"params\":{\"name\":\"mcp-adapter/execute-ability\",\"arguments\":{\"name\":\"jab/get-beers\",\"arguments\":{\"include_ids\":$KNOWN_IDS}}}}" \
  | jq '.result.beers | length'
```

**Expect:** exactly `30`. If it returns `25`, the auto-raise didn't fire and the silent-truncation regression is back.

## Smoke 8 — taxonomy filter dropping unknown keys (SYNC-4)

```bash
# Real taxonomy slug — should return beers tagged with that term.
curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"taxonomy":{"beer-type":["ipa"]},"numberposts":5}}}}' \
  | jq '.result.beers | length, map(.["beer-type"] | map(.slug))'

# Unknown taxonomy key — silently dropped. Result set should match an unfiltered call.
curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"taxonomy":{"private_unknown":["leak"]},"numberposts":5}}}}' \
  | jq '.result.beers | length'
```

**Expect:** first call returns beers whose `beer-type` includes `ipa`. Second call returns 5 (the default page) — the unknown taxonomy filter was dropped silently, no `tax_query` applied.

## Smoke 9 — `modified` / `modified_gmt` on every row (SYNC-5)

```bash
curl -ks $TR_AUTH "$TR_BASE/wp-json/mcp/v1/tools/call" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mcp-adapter/execute-ability","arguments":{"name":"jab/get-beers","arguments":{"numberposts":5}}}}' \
  | jq '.result.beers | map({id, modified, modified_gmt})'
```

**Expect:** every beer has both `modified` and `modified_gmt` populated with RFC3339 strings. They should equal each other (plugin emits the GMT value in both keys for WP REST envelope parity). No beer has `null` here — if any beer hits the fallback chain to epoch, that's a real publish-date integrity issue on that specific row, not a plugin bug.

## Smoke 10 — capability filter blocks unauthorized callers

Add a temporary mu-plugin at `wp-content/mu-plugins/zz-smoke-site-cap.php`:

```php
<?php
// SMOKE ONLY — DELETE AFTER VERIFYING.
add_filter( 'jab/headless_kit/site_manifest_capability', function () {
    return 'manage_options';
} );
```

Then:

```bash
# As a Subscriber-tier service user (whose App Password we have), this should now 401/403.
curl -ks $TR_AUTH -o /dev/null -w "%{http_code}\n" "$TR_BASE/wp-json/jab/v1/site"

# As an admin user, still 200.
curl -ks -u <admin>:<admin-app-password> -o /dev/null -w "%{http_code}\n" "$TR_BASE/wp-json/jab/v1/site"
```

**Expect:** `401` (or `403`) for the Subscriber, `200` for the admin. **Delete the mu-plugin afterwards.**

## Pass/fail rubric

- **Pass and tag:** all 10 smokes green → ready to `git tag plugin-v0.7.0` and push the tag to trigger the release workflow.
- **Pass except #10:** ship anyway, file a follow-up to investigate the auth filter.
- **Fail #1–#3:** STOP. Something fundamental is wrong with the integration. Do not tag.
- **Fail #5–#7:** SYNC-1..3 regression. Revert v0.7.0's `build_query_args` changes via `git revert <commit-sha>` and re-investigate the unit tests against the failing real-world case.
- **Fail #9 (missing `modified` field on any row):** REQUIRED-field validation failure on the row. Check `resolve_modified_date`'s fallback chain.

## After smoke passes

1. `git tag plugin-v0.7.0 && git push origin plugin-v0.7.0` to trigger `.github/workflows/release-plugin.yml`.
2. Verify the CI-built zip attached to the GitHub Release matches the local zip at `packages/wp-plugin/dist/wp-headless-kit-0.7.0.zip` (within a few bytes — timestamps will differ).
3. Delete the temporary `zz-smoke-site-cap.php` mu-plugin if you left it.
4. Move on to Phase 1 (real WordPress integration test harness) so this checklist becomes a much smaller, mostly-automated exercise next release.
