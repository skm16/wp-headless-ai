# wp-plugin v0.6.0 — Typed-Block Moat Design Spec

**Status:** Approved 2026-05-25. Ready for plan + implementation.

## Why this release exists

v0.5.0 shipped block-aware content emission: every CPT-list and by-slug ability can now opt into raw `post_content`, a parsed `blocks` tree, and a rendered HTML string. The blocks tree is structurally correct — every node carries WP's canonical `{ blockName, attrs, innerBlocks, innerHTML, innerContent }` shape — but it's **typed loosely**. Every block's `attrs` is `Record<string, unknown>`. ACF Blocks (`acf/*`) ship their field values as raw attachment IDs and unwalked Flex Content arrays. The CLI's `jab sync` can't pick up the new optional `content` / `blocks` / `rendered_content` keys because there's no manifest endpoint surfacing the input/output schemas.

v0.6.0 closes those three gaps. It is the "typed-block moat" release: per-block-type discriminated unions, ACF Block enrichment, and a manifest endpoint for CLI integration. Together these turn the v0.5.0 block tree from "the AI can see your blocks" into "the AI knows what each block is and how to read it." Nobody else ships per-site typed block schemas — this is the differentiator the kit was always going to need before public release.

## Scope

**In scope:**

1. **Per-block-type discriminated unions** — derived from `WP_Block_Type_Registry`. The `BlockNode` schema becomes a `oneOf` over one variant per registered block + one permissive fallback for unknown/third-party blocks not in the registry at request time.
2. **ACF Block (`acf/*`) attribute enrichment** — when an ACF Block has a bound field group, its `attrs.data` runs through the existing `walk_and_enrich()` so image fields resolve to attachment objects and nested Flex Content gets the same `oneOf` discriminator treatment as post-meta-bound ACF.
3. **Manifest endpoint** — new REST route at `/wp-json/jab/v1/manifest` returning the full ability roster (names, schemas, metadata) for CLI consumption.

**Out of scope (deferred again):**

- `jab/get-page-schema` aggregator — still no pilot evidence demanding fewer round-trips
- Per-block `rendered_html` (vs the top-level `rendered_content` v0.5.0 already ships) — wait for actual demand
- `BlockExpander::load_reusable_blocks` per-request memoization — wait for profile data showing it's hot
- `wp_block` CPT auto-discovery via Registry — inline expansion still covers the use case
- Runtime source-attribute extraction (we type sourced attributes in the schema but don't try to parse them out of `innerHTML`)

## Architecture

Three new files, two existing files touched. The new files form a small "block-typing" subsystem that complements (does not replace) the v0.5.0 `BlockSchema` / `BlockParser` / `BlockExpander` set.

### New

- **`includes/Schema/BlockTypeSchema.php`** — walks `WP_Block_Type_Registry` and emits the `oneOf` array of per-block-type variants + the unknown-fallback variant. Called once per ability-registration cycle; cached in a static array on the class. The discovery itself is cheap (sub-millisecond on typical sites); the cache exists so multiple ability registrations in the same request don't redundantly walk the registry.

- **`includes/Acf/BlockFieldSchema.php`** — walks ACF field groups looking for `block==<name>` location rules. Returns the same JSON Schema fragment shape `AcfSchema::for_post_type()` returns today (an object schema with image/media/Flex Content handling), keyed by block name. Used by `BlockTypeSchema` when emitting the `attrs.data` slot for `acf/*` variants.

- **`includes/Rest/Manifest.php`** — REST route at `/wp-json/jab/v1/manifest`. Auth gate mirrors `Rest\ContentTypes` (Application Password, `read` capability). Returns `{ plugin_version, generated_at, abilities: [{ name, category, label, description, input_schema, output_schema, meta }] }`.

### Modified

- **`includes/Schema/BlockSchema.php`** — `block_node_schema()` becomes a `oneOf` rather than a single object. Composition: `BlockTypeSchema::all_variants()` returns the array of known variants; `BlockSchema::block_node_schema()` appends its own unknown-fallback variant and wraps. Existing consumers of `BlockSchema::block_array_schema()` (the list + by-slug abilities) need no signature change.

- **`includes/Schema/BlockParser.php`** — `normalize()` checks whether the block is ACF-namespaced (`acf/*`) and, if so, runs `attrs.data` through `walk_and_enrich()` using the schema from `BlockFieldSchema::for_block_name()`. Non-ACF blocks pass through unchanged. The walker call is gated by `function_exists('acf_get_block_types')` so the plugin still works on sites without ACF.

- **`wp-headless-kit.php`** — registers `Rest\Manifest::register()` alongside the existing `Health` and `ContentTypes` registrations.

### Untouched (deliberate)

- `BlockExpander` — current cycle-bounded inline expansion remains correct.
- The `include` flag input — already covers the surface area; no new flags needed.
- `PostTypeListAbility` / `PostTypeBySlugAbility` — the new typed schema flows through transparently because they consume `BlockSchema::block_array_schema()` as opaque output-schema input.

## Discriminated-union shape

The v0.5.0 `block_node_schema()` is a single object with `attrs: { type: 'object', additionalProperties: true }`. v0.6 changes it to:

```
{
  oneOf: [
    <variant for core/paragraph>,
    <variant for core/heading>,
    ...
    <variant for acf/hero>,
    ...
    <unknown-block fallback variant>     // must be LAST
  ]
}
```

### Per-block-type variant

```
{
  type: "object",
  additionalProperties: false,
  required: ["blockName", "attrs", "innerBlocks", "innerHTML", "innerContent"],
  properties: {
    blockName: { type: "string", enum: ["core/paragraph"] },   // discriminator
    attrs: <derived from block.json attributes>,
    innerBlocks: { type: "array", items: { type: "object", additionalProperties: true } },
    innerHTML: { type: "string" },
    innerContent: { type: "array", items: { oneOf: [{type:"string"},{type:"null"}] } }
  }
}
```

**Discriminator uses `enum: ["<name>"]`, NOT `const: "<name>"`** — same trick the Flex Content fix used in v0.4. WP core's `rest_validate_value_from_schema` silently ignores `const`; every variant would accept every value and `rest_find_one_matching_schema` would reject the response with "matches more than one of the expected formats." `enum` validates correctly.

### Unknown-fallback variant (last in `oneOf`)

```
{
  type: "object",
  additionalProperties: false,
  required: ["blockName", "attrs", "innerBlocks", "innerHTML", "innerContent"],
  properties: {
    blockName: { oneOf: [{type:"string"},{type:"null"}] },   // null for freeform wrapper
    attrs: { type: "object", additionalProperties: true },
    innerBlocks: { type: "array", items: { type: "object", additionalProperties: true } },
    innerHTML: { type: "string" },
    innerContent: { type: "array", items: { oneOf: [{type:"string"},{type:"null"}] } }
  }
}
```

This variant handles three cases:
1. Third-party blocks not registered at request time (rare but real — some plugins register blocks only on specific admin screens).
2. The "freeform" wrapper `parse_blocks()` emits for classic/page-builder content (`blockName === null`).
3. Blocks whose registered `attributes` definition is malformed or empty.

### `block.json` `source` handling

WP block attributes can declare `source: 'attribute' | 'html' | 'query' | 'text'`. These values are extracted from HTML markers at render time, not stored in the block's stored `attrs` array. Strategy:

- **Sourced attributes go into the variant's `attrs.properties` map** with their declared `type`. They are **NOT added to `attrs.required`**, so runtime validation passes even when the value is absent (which is the common case — `parse_blocks()` only returns stored attrs).
- **The variant's `attrs` is still `additionalProperties: false`** — sourced attributes are known schema properties at this point, not stragglers.

The result: the TypeScript type the SDK generates correctly marks sourced attributes as `?`-optional, and code paths that read them from a rendered HTML response (e.g., after `the_content` filtering) get proper typing without runtime validation failing for the parsed-tree-only case.

Blocks with no declared `attributes` (rare; usually utility blocks like `core/spacer`) get `attrs: { type: 'object', additionalProperties: true }` — fully permissive. The variant is still emitted so the `blockName` discriminator works.

## ACF Block enrichment

ACF Blocks register via `acf_register_block_type` and store all their field values inside a single `data` key in the block's `attrs`. The values are raw — image fields are attachment IDs, nested Flex Content is unwalked arrays.

### Schema-side: `Acf\BlockFieldSchema`

Mirrors `AcfSchema::for_post_type()` but walks `block==<name>` location rules instead of `post_type==<name>`. Returns the same kind of object-schema fragment AcfSchema already produces (with `oneOf` discriminators for Flex Content, `x-acf-media` markers for image fields, etc.).

`BlockTypeSchema` calls this when emitting an `acf/*` variant and sets `attrs.data` to the returned fragment. Variants for ACF Blocks whose field group hasn't been registered (or who have no bound fields) get the generic `attrs: { additionalProperties: true }` fallback.

### Runtime-side: `BlockParser::normalize()` extension

When normalizing a node, if `blockName` starts with `acf/` and ACF is active, look up the field group schema for that block and walk `node.attrs.data` through `walk_and_enrich()`. The walker is the same one `PostTypeListAbility` uses for post-meta-bound ACF — image enrichment, Flex Content variant picking, format-validation drops are all reused.

Gate the call by `function_exists('acf_get_block_types')` and `function_exists('get_fields')` so the plugin still works on ACF-free sites.

## Manifest endpoint

`GET /wp-json/jab/v1/manifest` — single read-only route.

**Auth:** Application Password authentication; user must have `read` capability. Mirrors `Rest\ContentTypes`.

**Response:**

```json
{
  "plugin_version": "0.6.0",
  "generated_at": "2026-05-25T10:00:00Z",
  "abilities": [
    {
      "name": "jab/get-posts",
      "category": "jab-content",
      "label": "Get Posts",
      "description": "...",
      "input_schema": { ... full JSON Schema ... },
      "output_schema": { ... full JSON Schema ... },
      "meta": { "mcp": { "public": true } }
    }
  ]
}
```

The schemas returned are the SAME schemas registered with the abilities API — no transformation. The CLI's `jab sync` consumes these and runs them through `json-schema-to-typescript` to regenerate `lib/sdk/types.ts`.

**Why a separate endpoint rather than MCP `tools/list`:** the MCP path requires session initialization and is meant for runtime tool discovery. The manifest is a static build-time artifact for the type generator. Keeping them separate also means the CLI doesn't need to speak JSON-RPC for the type-regen path — a plain authenticated `GET` is enough.

## Data flow

**Ability registration time** (`Registry::register_abilities()`, hooked on `wp_abilities_api_init`):

1. `BlockTypeSchema::all_variants()` runs once. It walks `WP_Block_Type_Registry::get_all_registered()`, emits per-block-type variants (using `BlockFieldSchema::for_block_name()` for `acf/*` blocks), and caches in a static array.
2. `BlockSchema::block_node_schema()` builds its `oneOf` by appending the unknown-fallback variant to `BlockTypeSchema::all_variants()`.
3. This composed schema becomes part of every CPT ability's `output_schema` via `BlockSchema::block_array_schema()`.
4. `Rest\Manifest::register()` hooks `rest_api_init` and registers the route.

**Request time** (`shape_row()` → `BlockParser::parse()` → `BlockExpander::expand()`):

1. `BlockParser::parse()` calls WP's `parse_blocks()` then `normalize()` per entry.
2. For each entry, `normalize()` checks `blockName`. If `acf/*` and ACF is active, walk `attrs.data` through `walk_and_enrich()` using the schema from `BlockFieldSchema::for_block_name()`. Otherwise pass through.
3. `BlockExpander::expand()` runs unchanged from v0.5 — recursive walk, `core/block` reference resolution, visited-set cycle bound.
4. The resulting tree validates against the new `oneOf` schema because every node's `blockName` matches exactly one variant (or the fallback).

**Manifest request time** (`GET /wp-json/jab/v1/manifest`):

1. Capability check + Application Password auth gate.
2. Query the WP Abilities API registry for all abilities in the `jab-content` category (plus the standalone `jab/get-menus` and taxonomy abilities).
3. Serialize each ability's name, label, description, schemas, and meta. Wrap in the envelope above.

## Caching

`BlockTypeSchema` keeps a static cache of generated variants for the request lifetime. This is enough because:

- Multiple ability registrations in the same `wp_abilities_api_init` cycle hit the cache after the first call.
- A new request gets a fresh PHP process (or worker), so the static cache rebuilds — which is fine because the work is sub-millisecond.

A transient cache (like `AcfSchema` uses) is **not** added in v0.6. The reasoning: `AcfSchema`'s transient pays for itself because ACF field group loading involves multiple `WP_Query` calls. `WP_Block_Type_Registry::get_all_registered()` is in-memory and cheap. Adding a transient buys nothing and adds invalidation complexity. If profile data later shows otherwise, we'll add one.

ACF Block field group resolution reuses `AcfSchema`'s existing per-request memoization implicitly — `acf_get_field_groups()` is already memoized in ACF core for the request lifetime.

## Error handling

**Missing block.json `attributes` definition:** emit the variant with permissive `attrs: { additionalProperties: true }`. Log a diagnostic ledger entry (mirrors the existing ACF diagnostics pattern) so agencies can see which blocks didn't type-tighten.

**Block type registered without a name** (malformed plugin): skip the variant entirely, log a `_doing_it_wrong()` breadcrumb. Mirrors the ACF Flex Content "no name" handling in v0.4.

**ACF Block with no bound field group:** emit the variant with permissive `attrs: { additionalProperties: true }`. No diagnostic — this is a valid state (the agency may register an ACF Block whose fields they declare elsewhere).

**Schema-validation failure under `oneOf`** (a runtime block whose attrs don't match its declared variant): this should be impossible because we control both schema emission and runtime enrichment. If it surfaces, it's a bug — let WP's REST validation throw, don't catch. The "errors are loud" principle from CLAUDE.md.

**Manifest endpoint authentication failure:** returns standard WP REST `401 / 403` per the auth gate.

## Testing strategy

Pure-unit tests with WP function stubs, same pattern as v0.5.0. New stubs needed in `tests/bootstrap.php`:

- `WP_Block_Type_Registry` singleton with `get_all_registered()` returning a canned map of block types.
- `acf_get_block_types()` — returns a map of registered ACF block names → config.
- `register_rest_route()` — records calls so manifest registration can be asserted.
- `acf_get_field_groups()` already callable; needs to be stubbed if not already (existing AcfSchema tests probably already cover this).

New test files:

- **`tests/unit/Schema/BlockTypeSchemaTest.php`** — variant generation per block type, unknown-fallback ordering (must be last), source-attribute handling, no-attributes-defined fallback.
- **`tests/unit/Acf/BlockFieldSchemaTest.php`** — location-rule walking, returns the same shape as AcfSchema, handles missing-block-name case.
- **`tests/unit/Schema/BlockParserTest.php`** (extended) — ACF Block enrichment cases: attrs.data with image field → resolves to attachment object; attrs.data with Flex Content → picks correct variant; non-ACF block → passes through unchanged.
- **`tests/unit/Rest/ManifestTest.php`** — endpoint registration, auth gate, response envelope shape, schemas-as-registered.

Existing tests must continue to pass — `PostTypeListAbilityBlockEmissionTest` in particular asserts the v0.5.0 generic shape. v0.6 changes the schema but not the runtime emission, so the runtime tests should remain green. The schema-shape test (`test_output_schema_declares_optional_block_fields`) will need updating to assert the new `oneOf` shape rather than the old generic-attrs shape.

## Migration / breaking-change analysis

**For existing SDK consumers:**

- Schema becomes more precise (`oneOf` discriminated union vs single object with permissive attrs). `json-schema-to-typescript` will emit a discriminated union: `type BlockNode = ParagraphBlock | HeadingBlock | ... | UnknownBlock`.
- Code that did `block.attrs.foo` for a known block type now type-checks more strictly — caller must narrow via `block.blockName === 'core/paragraph'` first. This is a **TypeScript-level breaking change** but a **runtime-compatible change** — the JSON returned is the same shape it was; only the type narrowing tightens.
- Run `jab sync` after upgrading; existing code that didn't narrow will get TypeScript errors pointing at exactly the lines that need fixing. This is the correct ergonomic.

**For agency mu-plugins:**

- No breaking changes to filter hooks.
- The new `Rest\Manifest` endpoint adds a route; no existing route changes.

**Plugin version bump:** 0.5.0 → 0.6.0 per the typing tightening + new endpoint. Not 0.5.1 because the type changes downstream are intentional and meaningful. Not 1.0.0 because we're still pre-stable.

## Release notes outline

The README's "What's new in 0.6.0" section will document:

- **TYPED-1 (Medium):** Per-block-type discriminated unions. Generated SDK types now narrow `BlockNode` by `blockName`.
- **TYPED-2 (Medium):** ACF Blocks (`acf/*`) get the full ACF enrichment treatment — image fields, Flex Content, etc. Closes the v0.5.0 known limitation.
- **CLI-1 (Low):** Manifest endpoint at `/wp-json/jab/v1/manifest` for CLI type generation. The CLI side (`jab sync` consumption) is a separate repo concern.
- **Migration:** type-only breaking change. Run `jab sync` after upgrade.

## Open questions / risks

**Unknown:** how does `WP_Block_Type_Registry::get_all_registered()` behave when called during `wp_abilities_api_init` vs `init` vs `rest_api_init`? Block registration usually happens on `init` priority 10. If `wp_abilities_api_init` fires earlier, we may see an incomplete registry. **Mitigation:** the plan should verify timing during execution. If the registry isn't ready yet, we re-walk it lazily on first ability call.

**Known:** sites with `register_block_type()` calls inside admin-only hooks won't have those blocks in the front-end registry. The unknown-fallback variant handles this correctly — those blocks just don't get tight typing.

**Known:** plugin updates that change block.json attributes mid-deploy can produce a transient mismatch between the schema cached in the CLI SDK and the response shape. Standard semver hygiene applies — agencies regenerate the SDK after a plugin update.
