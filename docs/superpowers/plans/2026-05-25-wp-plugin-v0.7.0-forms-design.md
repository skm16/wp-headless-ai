# Gravity Forms support — design for `packages/wp-plugin` v0.7.0 → v0.7.2

> Status: APPROVED DESIGN — anchors v0.7.0 → v0.7.2 implementation
> Author: Sean + Claude (senior WP dev, JAB)
> Date: 2026-05-25
> Plugin baseline: v0.6.0

## Context

JAB's positioning is "out-deliver Automattic on agency-facing DX, don't out-engineer them on the protocol." Forms are the most common request agencies will hit on day one of a headless migration — they sit at the intersection of marketing-team data capture and CRM/email automation. Until 2026-05-25, root `CLAUDE.md` listed forms as deliberately out-of-scope for v1 (both the "Anti-patterns to avoid" and "Out of scope for v1" sections). The user reopened that scope on 2026-05-25, **starting with Gravity Forms** but with portability to other form plugins (WPForms, Forminator, Fluent Forms) as a downstream goal.

This document investigates how the WP plugin should add Gravity Forms support, lays out 4 candidate approaches with pros/cons, and recommends one. The four open decisions raised during planning were resolved on the same day (see [Resolved decisions](#resolved-decisions-2026-05-25) below).

**User-stated constraints (2026-05-25):**
- **Scope:** Kit only (plugin + CLI). SaaS implications deferred.
- **Add-on compatibility is mandatory:** Constant Contact, Mailchimp, and similar GF add-ons MUST fire on submission. E-commerce / payment add-ons are deferred.
- **Recommend one** approach, not just present them.

### Constraints surfaced during exploration

1. **Every existing ability is read-only.** Forms introduce the first write ability — that establishes new patterns for mutation permissions, anti-spam, rate limiting, and idempotency that the codebase has no precedent for.
2. **GF's REST API does not export form definitions as JSON Schema.** `GET /forms/{id}` returns GF's own form-object shape; conditional logic, calculations, and validation rules are not structured for headless consumption. **Any typed-DX path requires us to derive schema PHP-side from `GFAPI::get_form()`.**
3. **Add-ons fire via the feed pipeline on submission.** This pipeline runs inside `GFAPI::submit_form()` and inside GF's `/wp-json/gf/v2/submissions` endpoint. Any submission path that doesn't call one of those silently breaks Constant Contact, Mailchimp, etc.
4. **CLI auto-regenerates from manifest.** If forms appear in `/wp-json/jab/v1/manifest`, they automatically get typed SDK functions on `jab sync` with no CLI changes. That's a strong reason to make form abilities first-class manifest entries.

## Approach 1 — Thin pass-through (proxy + docs only)

**The idea:** Add zero new abilities. Document how the headless frontend talks directly to Gravity Forms' existing `/wp-json/gf/v2/` REST API. The plugin's only job is to make sure the auth model works (likely a thin proxy ability that forwards Application-Password auth to GF's REST, which normally requires OAuth1 consumer keys).

### Pros
- **Smallest plugin surface.** Possibly under 100 lines of PHP. Matches the "plugin should be boring" coaching reminder.
- **Survives GF upgrades unchanged.** We're not modeling GF's field types; GF owns that contract.
- **Add-ons work for free** — GF's REST `/submissions` endpoint runs the same feed pipeline.
- **No new write-permission patterns** in the plugin layer.

### Cons
- **Zero typed DX.** The kit's "magical first 10 minutes" promise vanishes for forms. Claude Code has nothing typed to scaffold from; the agency dev hand-writes the form, hand-defines field types, hand-wires submit.
- **Auth model conflict.** GF REST defaults to OAuth1 consumer key/secret, not Application Passwords. We'd need either a server-side proxy (which is then 2/3 of Approach 2 anyway) or to document a non-JAB-native auth path.
- **Forms don't appear in `/wp-json/jab/v1/manifest`** → CLI generates nothing → no `lib/sdk/forms.ts`.
- **Portability story collapses.** Every form plugin (WPForms, Forminator) has a different REST API shape; we'd be writing N integration docs, not building a portable abstraction.

**Verdict:** Cheapest to ship, weakest agency value. Fine as a fallback for "experts who want to bypass JAB," not as the primary story.

## Approach 2 — Schema-first, abilities-based (the JAB-native way) **← recommended**

**The idea:** Treat GF forms the way ACF field groups are treated today. Introspect each registered form via `GFAPI::get_form()` PHP-side, derive a JSON Schema for the form's submission payload, and register three new abilities:

| Ability | Type | Behavior |
|---|---|---|
| `jab/list-forms` | read | Returns `[{id, title, slug, is_active, field_count}]` for all GF forms |
| `jab/get-form` | read | Returns one form's structured definition (fields normalized to a JAB-canonical taxonomy — see below) |
| `jab/submit-form-<slug>` | **write (first in the plugin)** | Calls `GFAPI::submit_form( $form_id, $input )` and returns GF's success/error response |

**Key idea — normalized field taxonomy.** Instead of leaking GF's field types directly, define a JAB-canonical field-type vocabulary (`text`, `email`, `textarea`, `select`, `radio`, `checkbox`, `number`, `hidden`, `file`, `date`, ...) that GF field types map to. WPForms / Forminator / Fluent Forms can later map into the same vocabulary. **This is the portability moat the user asked about** — the agency frontend doesn't change when the form plugin changes.

**Schema shape:** per-form `jab/submit-form-<slug>` ability with a narrow input schema covering just that form's normalized fields. Pattern mirrors how post types already become `jab/get-<plural>` / `jab/get-<singular>-by-slug` via auto-discovery. Conditional logic surfaces as `x-jab-conditional` schema metadata (renderer-honored, schema-safe).

**Submission path:** `execute_callback` → `GFAPI::submit_form()` → GF runs validation → GF fires feeds (Constant Contact, Mailchimp) → returns `{is_valid, validation_messages, confirmation_message|confirmation_redirect, entry_id}`. Add-ons work because we're calling GF's own entry point.

**New PHP surface estimate:**
- `includes/Forms/Registry.php` — discover GF forms, auto-register abilities (~120 lines)
- `includes/Forms/Schema.php` — field-type taxonomy + JSON Schema derivation (~400–500 lines, mirrors `Acf/Schema.php` complexity)
- `includes/Forms/SubmitAbility.php` — write ability, calls `GFAPI::submit_form()` (~150 lines)
- `includes/Forms/Permissions.php` — write-permission pattern, anti-spam hooks (~80 lines)

### Pros
- **Maximum typed DX.** `await submitContactForm(client, { email, message, topic: 'sales' })` — fully typed, IDE autocomplete, Claude Code can scaffold a renderer from the schema in seconds.
- **Follows existing plugin patterns** (ACF Schema, BlockSchema with `oneOf` discriminators) — anyone who's read the plugin will recognize the shape.
- **Add-ons fire correctly** — submission goes through `GFAPI::submit_form()`.
- **Forms appear in the manifest** → CLI auto-regenerates → `lib/sdk/forms.ts` ships on `jab sync`.
- **Portability moat:** normalized field taxonomy means WPForms support later is "another adapter under `Forms/`", not "rewrite the frontend SDK."
- **Uses Application Passwords** — consistent with the rest of the kit.

### Cons
- **Largest PHP surface.** ~750–900 lines across 4 new classes. Closest the plugin has come to "interesting" — counter to the "plugin should be boring" coaching reminder.
- **Establishes the first write-ability pattern** — has to make permission, rate-limit, anti-spam decisions that didn't need to exist before. Reasonable scope; just not "boring."
- **File uploads are awkward** — multipart vs JSON-first SDK. Likely a two-step pattern: `jab/upload-form-file` → returns token → token included in `submit-form` payload. Mirrors how WP REST handles media. Adds ~150 lines.
- **Conditional logic / multi-page** in v1 surfaces as schema metadata only — frontend renderer can choose to honor or ignore. Full UX parity with GF's rendered HTML is deferred.
- **GF version coupling.** Every GF major release that changes field semantics is a plugin update for us.

## Approach 3 — Hybrid: JAB owns submission, GF owns schema

**The idea:** A middle path. Add `jab/get-form` that returns the **raw (or lightly normalized) GF form JSON** — no fancy JSON Schema derivation, no per-form types. Add `jab/submit-form` (write ability) that proxies to `GFAPI::submit_form()`. On the frontend side, the kit ships **one generic `<JabGravityForm formId={3} />` React component** in `packages/frontend-template/` that dynamically renders any GF form.

### Pros
- **Mid effort PHP-side** — schema work is minimal; we're just pass-through on the read side. Maybe 300 lines total.
- **Add-ons work** — submission still goes through `GFAPI::submit_form()`.
- **One renderer covers every form**, including forms created AFTER the last `jab sync` (zero regen needed for new forms).
- **Closer to GF's own behavior** — devs who know GF aren't surprised by mismatched semantics.

### Cons
- **Loses the typed-DX moat.** Every form looks like `Field[]` not `{ email: string; topic: 'sales'|'support' }`. Claude Code can't introspect a specific form's shape from the SDK.
- **The generic renderer is a monolith** — it must support every field type, conditional logic, validation, file upload, anti-spam, multi-page. One large component that's hard to iterate on with Claude Code (the opposite of the kit's design ethos).
- **No incremental escape hatch.** Once an agency dev needs to customize a specific form, they fork the renderer wholesale. Forking the whole renderer is a big jump from editing scaffolded code.
- **Portability story is medium.** GF/WPForms/Forminator field shapes differ enough that the "generic renderer" balloons or branches per plugin.

## Approach 4 — MCP-tools-only (agent-driven, no SDK generation)

**The idea:** Register `jab/list-forms`, `jab/get-form`, `jab/submit-form` as MCP tools, but mark them `meta.mcp.public => true` *without* exposing them in `/wp-json/jab/v1/manifest` (i.e., they don't generate frontend SDK code). They exist so Claude Code can test submissions, query form definitions, and help the dev scaffold ad-hoc, but the dev writes their own form components from scratch each time.

### Pros
- **Smallest surface that still gives Claude Code something to work with.**
- **No commitment to a field-type taxonomy** — defers the hard portability decision.
- **Useful for headless devs who picked a different form library** and just want Claude Code to push entries to GF.

### Cons
- **Worst DX.** Nothing useful in `lib/sdk/forms.ts`. The agency dev still hand-builds every form.
- **Doesn't move the needle on the "more meaningful for agencies" thesis** — which is exactly the motivation the user gave.
- **Easy to skip.** Agencies will just use GF's REST or roll their own; the JAB plugin doesn't add value.

---

## Recommendation: **Approach 2 (schema-first) with a normalized field-type taxonomy**

### Why

1. **It's the only approach that delivers the agency-DX moat** the user explicitly asked for. `await submitContactForm(client, { email, message })` with full IDE autocomplete is what makes the plugin "meaningful for agencies." Approach 1 gives them nothing typed; Approach 3 gives them generic `Field[]`; Approach 4 gives them MCP-only.
2. **It satisfies the add-on requirement** — `GFAPI::submit_form()` fires Constant Contact, Mailchimp, and every other feed-based add-on without us touching their code paths.
3. **It builds the portability moat.** Normalizing GF field types into a JAB-canonical vocabulary means WPForms/Forminator support later is an adapter, not a rewrite. This is the "more meaningful for agencies" multiplier — the same agency frontend works regardless of which form plugin the client picked.
4. **It follows existing plugin patterns.** `Acf/Schema.php` and `Schema/BlockSchema.php` already model this exact "introspect → discriminated-union JSON Schema" shape; the `oneOf`-on-`acf_fc_layout` pattern transfers directly to per-form ability schemas.
5. **The boring-plugin guardrail bends, doesn't break.** Yes, this is the most code we've added in one feature. But the code is mechanically similar to ACF/block schema work — it's not novel territory, it's the same pattern applied to a new domain.

### Phasing (v0.7.0 → v0.7.x)

| Phase | Deliverable |
|---|---|
| **v0.7.0** | Read path: `jab/list-forms`, `jab/get-form`. Normalized field taxonomy covering text, email, textarea, select, radio, checkbox, number, hidden, date. Schema appears in manifest. CLI regen produces `lib/sdk/forms.ts`. No submission yet — frontend can render forms but submits are wired by the dev. |
| **v0.7.1** | Write path: `jab/submit-form-<slug>`. Establishes write-ability pattern in `Forms/Permissions.php`. Honeypot + reCAPTCHA verification passthrough. Returns `{is_valid, validation_messages, confirmation, entry_id}`. Constant Contact + Mailchimp add-ons verified working end-to-end on a test install. |
| **v0.7.2** | File-upload path: `jab/upload-form-file` → token → included in submit payload. Conditional-logic schema metadata (`x-jab-conditional`) for renderer honoring. |
| **Deferred (v0.8+)** | Multi-page, calculations, signature, payment add-ons, list field, repeaters. |

### Why this phasing

- v0.7.0 ships **typed reads** before the harder write/anti-spam decisions. Agency devs get the "look, Claude Code already knows your form's field types" demo on day one, with no submission risk yet.
- v0.7.1 is where the first-ever write ability lands. Putting it in its own minor release isolates the permissions/anti-spam pattern decisions for review.
- v0.7.2 closes the realistic feature gap for marketing-site forms (uploads + simple conditionals).

## Verification plan (when implementation lands)

1. **Plugin install on a GF-equipped test WP:** confirm `class_exists('GFAPI')` gates the boot. Plugin must be inert on installs without GF.
2. **Manifest endpoint:** `curl /wp-json/jab/v1/manifest` returns `jab/list-forms`, `jab/get-form`, and one `jab/submit-form-<slug>` entry per registered form. Verify schemas pass `json-schema-to-typescript` compile cleanly.
3. **CLI regen:** `jab sync` against the test WP produces `lib/sdk/forms.ts` containing `listForms()`, `getForm()`, and per-form `submit<FormSlug>Form()` input types. Type-check the generated file with `tsc --noEmit`.
4. **Add-on smoke test (v0.7.1):** install Mailchimp add-on, configure a feed on a test form, submit via the per-form submit ability, confirm a contact appears in Mailchimp. Repeat for Constant Contact. **This is the gating test for v0.7.1 ship.**
5. **Conditional logic schema visibility (v0.7.2):** create a GF form with a "show if topic == sales" rule, verify `x-jab-conditional` appears in the emitted schema and survives `json-schema-to-typescript` (the library ignores unknown `x-*` keys, which is the desired behavior).
6. **Spam path:** confirm GF's honeypot field is included in the schema with `x-jab-honeypot: true`, and that submitting with the honeypot populated returns `is_valid: false` from GF's pipeline (not a JAB-side reject — GF owns spam logic).
7. **Anonymous-submit override:** confirm that setting `add_filter( 'jab/headless_kit/forms/allow_anonymous_submit', '__return_false' )` causes anonymous submissions to be rejected with a 403, and that a per-form `jab/headless_kit/forms/{form_id}/capability` filter narrows further.
8. **Rate-limit hooks:** confirm `do_action( 'jab/forms/before_submit', ... )` fires before `GFAPI::submit_form()` and that returning `true` from `apply_filters( 'jab/forms/should_throttle', false, ... )` short-circuits with a 429 response.

## Resolved decisions (2026-05-25)

All four open items raised during planning were resolved in favor of the recommended option.

### 1. Submit ability shape — **per-form**

Each GF form generates its own `jab/submit-form-<slug>` ability (mirrors how post types already become `jab/get-<plural>` and `jab/get-<singular>-by-slug`). Input schema is narrow to that form's normalized fields, so the generated SDK gets `submitContactForm({ email, message })` with no discriminated-union helpers required on the consumer side. Manifest entry count grows linearly with form count — acceptable given the plugin already follows the same pattern for post types and taxonomies.

**Implementation note:** if the manifest grows uncomfortably large on a site with many forms, we revisit by adding a polymorphic `jab/submit-form` as an *additional* escape-hatch ability (not as a replacement) in a later release.

### 2. Conditional-logic schema — **JAB-canonical shape**

`x-jab-conditional` metadata uses a JAB-canonical vocabulary that references JAB field keys (not GF field IDs):

```json
{
  "x-jab-conditional": {
    "action": "show" | "hide",
    "logic": "all" | "any",
    "rules": [
      { "field": "<jab-field-key>", "operator": "is" | "is_not" | "contains" | "starts_with" | "ends_with" | "greater_than" | "less_than", "value": "<scalar>" }
    ]
  }
}
```

Mapping from GF's internal conditional-logic JSON to this shape lives in `Forms/Schema.php` (~50 lines). The mapping is the same pattern we'd reuse when adding WPForms / Forminator adapters later — the canonical vocabulary is the contract every adapter speaks.

### 3. Submit-ability auth — **filter-gated, anonymous by default**

Default behavior matches GF's own behavior on a standard WP site: anonymous submissions are accepted. Agencies override via two filters:

- `jab/headless_kit/forms/allow_anonymous_submit` (bool, default `true`) — global on/off for anonymous submissions across all forms.
- `jab/headless_kit/forms/{form_id}/capability` (string|null, default `null`) — per-form required capability. When set, the submit ability's `permission_callback` requires `current_user_can( $capability )`. Consistent with the existing `jab/headless_kit/ability_capability` filter pattern in [Permissions.php](../../../packages/wp-plugin/includes/Abilities/Permissions.php).

GF's own honeypot field is honored — it surfaces in the schema as `x-jab-honeypot: true` and the submission path lets GF's own validation pipeline reject populated honeypots.

### 4. Rate limiting — **hook-based, no built-in limiter**

The plugin fires two hooks during the submission lifecycle and ships no built-in limiter:

- `do_action( 'jab/forms/before_submit', int $form_id, WP_REST_Request $request )` — agencies hook here for logging, counting, or short-circuiting via `wp_die()`.
- `apply_filters( 'jab/forms/should_throttle', bool $throttle, int $form_id, WP_REST_Request $request )` — when returning `true`, the submit ability returns a 429-equivalent response without calling `GFAPI::submit_form()`.

Plugin stays boring; the README documents recommended setups: Cloudflare rate-limit rules (free tier), WordFence / Sucuri rules, or a 20-line transient-based snippet agencies can paste into their theme's `functions.php` if they're on a shared host without a WAF.

## Out of scope for this design

- WPForms / Forminator / Fluent Forms support (the adapter pattern enables it; the implementation is a separate v0.8+ project).
- Form **rendering** components (`<JabGravityForm />`). The plugin emits schema + submission; the frontend-template can add an opinionated renderer in a future kit minor release. v0.7.x ships only the data plane.
- SaaS / `apps/web` integrations.
- Payment, signature, calculations, multi-page, list-field, repeater field types.
