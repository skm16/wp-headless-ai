# wp-headless-kit — Frontend Template

A starter Next.js (App Router, TypeScript, Tailwind) project that consumes a typed SDK generated by `@skm/wp-headless-cli`. Server-rendered, ISR-friendly, credentials-never-in-browser.

## Quick start

```bash
# 1. Copy the env template and fill in your WP details
cp .env.example .env.local
# edit .env.local: WP_URL, WP_USER, WP_APP_PASSWORD

# 2. Discover abilities + persist manifest (run from monorepo root)
pnpm exec wpheadless init "$WP_URL" \
  --user="$WP_USER" \
  --password="$WP_APP_PASSWORD" \
  --output=packages/frontend-template

# 3. Emit the typed SDK into lib/sdk/
pnpm exec wpheadless generate packages/frontend-template

# 4. Run the dev server
pnpm --filter @skm/wp-headless-frontend-template dev
```

Visit http://localhost:3000 — the home page links to `/beers`, which renders live beer data from your WP install with full ACF fields if available.

## Layout

```
packages/frontend-template/
├── app/
│   ├── layout.tsx           ← root layout + global styles
│   ├── page.tsx             ← home / setup checklist
│   ├── globals.css          ← tailwind directives
│   └── beers/
│       └── page.tsx         ← example: typed getBeers(skmClient) call
├── lib/
│   ├── sdk/                 ← GENERATED. Owned by `wpheadless generate`.
│   │                         (gitignored; runs after `wpheadless init`+`generate`)
│   └── skm/
│       └── client.ts        ← env-driven SkmClient singleton — hand-crafted, kept across regens
├── .env.example
├── next.config.ts
├── tailwind.config.ts
├── tsconfig.json
└── package.json
```

The split between `lib/sdk/` and `lib/skm/` is intentional: `lib/sdk/` is fully owned by the CLI's `generate` command and gets blown away on every regen. `lib/skm/` is hand-crafted glue (the env-driven client wrapper, request helpers, opinionated patterns) that survives regenerations.

## What's already wired

- **Server-only credentials** — `lib/skm/client.ts` reads env vars and is gated by `import "server-only"`. Importing it from a Client Component throws at build time.
- **ISR by default** — `app/beers/page.tsx` exports `revalidate = 60` so beers re-fetch every minute. Tune per-route.
- **Tailwind + the App Router** — minimal config, no opinions about UI design.

## What's NOT included (deliberately, per CLAUDE.md)

- WP search replacement
- Preview-mode wiring
- Multilingual support
- WooCommerce integration

These are real future work but obscure the v1 wedge if added now.

**Forms — reopened 2026-05-25:** Gravity Forms support is planned for plugin **v0.7.x** (typed reads in v0.7.0, write path in v0.7.1, file uploads in v0.7.2), with portability to WPForms / Forminator / Fluent Forms as a downstream goal via a normalized JAB field-type taxonomy. Design doc: [`docs/superpowers/plans/2026-05-25-wp-plugin-v0.7.0-forms-design.md`](../../docs/superpowers/plans/2026-05-25-wp-plugin-v0.7.0-forms-design.md). Not yet shipped — no form components in the template today.

## Adding more pages

The fastest path is to clone `app/beers/page.tsx`. The pattern is:

```tsx
import { skmClient } from "@/lib/skm/client";
import { getX } from "@/lib/sdk";

export const revalidate = 60;

export default async function XPage() {
  const result = await getX(skmClient);
  return /* render result.* */;
}
```

Every ability registered in the WP plugin gets a `getX` function in the SDK. Run `pnpm exec wpheadless sync packages/frontend-template` after WP-side schema changes.

## TLS / LocalWP note

LocalWP uses self-signed certs. For dev only:

```bash
NODE_TLS_REJECT_UNAUTHORIZED=0 pnpm --filter @skm/wp-headless-frontend-template dev
```

Never set this in CI or production environments.
